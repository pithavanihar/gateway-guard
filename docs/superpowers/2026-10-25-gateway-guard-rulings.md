# gateway-guard v1: decisions made during the build

Every ruling the build controller made on the owner's behalf, in order, with what it costs if wrong. Source: the SDD ledger for docs/superpowers/plans/2026-10-25-gateway-guard-library.md.

- Ruling: R1 — add `.prettierignore` containing `docs/` and `.superpowers/` in Task 1 — design docs are prose not owned by the formatter — cost if wrong: docs unformatted (cosmetic).
- Ruling: R2 — `Router.candidates(method, {avoid})` returns usable non-avoid gateways in priority order, then `avoid` (if usable), then remaining unusable ones ordered by lowest failureRate; `choose()` = first of `candidates()` with its reason — keeps choose/candidates one rule — cost if wrong: creation-time failover order differs slightly.
- Ruling: R3 — import `randomUUID`, `createHmac`, `timingSafeEqual` from `node:crypto` (not the global) — Node 18 floor — cost if wrong: none.
- Ruling: R4 — work on branch feat/v1 of a brand-new repo; main holds only the docs commit — no consent needed for a repo with no prior history; merge happens at finish — cost if wrong: trivial.
- Ruling: R5 — add `.gitattributes` (`* text=auto eol=lf`) in Task 2's commit — implementer flagged CRLF checkouts could break format:check on Windows — cost if wrong: none.
- Ruling: R6 — `all-down` takes precedence over `retry` in Router.choose (check nothing-usable first); Task 7 implementer makes this one-line change in Router.ts with a test — Task 7 keys the spec §6.3 "all down" event off reason === "all-down", which must fire on retries too — cost if wrong: a retry log line says all-down instead of retry.
- Ruling: R7 — keep `NoGatewayAvailableError` when `exclude` empties the list; Task 7 calls `candidates()` once and iterates that list for creation-time failover (never re-calls with exclude) — avoids exception-driven control flow — cost if wrong: none for v1 callers.
- Ruling: R8 — accept `StatusResult = {status: AttemptStatus} & Partial<Omit<Outcome,"status">>` as the fetchStatus return type (plan's intersection type couldn't express "created") — Task 6 and 7 use StatusResult — cost if wrong: none (wider type).
- Ruling: R9 — `payment_timed_out` is classified by its error_source (customer → customer; bank/gateway/issuer/network/razorpay → gateway; otherwise unknown) instead of always customer — docs say it can mean the gateway didn't respond, and miscounting a gateway timeout as customer hides an outage (spec anti-goal is the mirror image) — cost if wrong: some customer abandonment counted as gateway when Razorpay reports a non-customer source.
- Ruling: R10 — `authentication_failed` gets the same source-based treatment as R9 — Razorpay also uses it for issuer 3DS/ACS failures; source-based keeps customer OTP failures as customer — cost if wrong: same as R9.
- Ruling: R11 — beneficiary_bank counts as gateway for source-decided reasons (consistent with the shared source table; payee's bank isn't customer-caused) — cost if wrong: payee-bank issues counted against the gateway.
- Ruling: R12 — CashfreeAdapter.createOrder validates its own limits before any request: amountMinor >= 100 (₹1) and phone = 10 digits or "+" international → ValidationError; customer_id is normalised to Cashfree's charset/length (strip disallowed chars, pad to 3, cap 50) rather than rejected. Task 7: a ValidationError from an adapter propagates to the caller (no health record, no creation failover) — it's caller input, not gateway health — cost if wrong: a payment Razorpay would accept fails fast when Cashfree is chosen.
- Ruling: R13 — add optional `cancelOrder?(gatewayRef): Promise<void>` to GatewayAdapter; Cashfree implements it by terminating the order (PATCH order_status TERMINATED per docs). Task 7 calls it for the previous attempt before routing a retry; if cancellation fails, the retry is refused with RetryNotAllowedError("status-unknown") — spec §6.4 errs on not double-charging — cost if wrong: retries refused during Cashfree API trouble.
- Ruling: R14 — Razorpay orders can't be cancelled, so Task 7 tracks paid attempts per orderId and emits `{ type: "order.multiple-payments", orderId, attempts }` when a second attempt for the same orderId is confirmed paid, so the consumer can refund — closes the spec §4 double-charge anti-goal as far as a library can — cost if wrong: an extra event type.
- Ruling: R15 — extract the duplicated header/signature helpers (header lookup, constant-time compare) into `src/adapters/signature.ts`, used by both adapters — reviewer would flag verbatim duplication — cost if wrong: none.
- Ruling: R16 — in Task 7, a cancelOrder rejection with reason "order_paid" triggers a fetchStatus re-check and then RetryNotAllowedError("paid"); TERMINATION_REQUESTED counts as cancelled, and a late payment is caught by R14's order.multiple-payments event — cost if wrong: none beyond R14.
- Ruling: R17 — accept `Router.plan()` (one ranking → order + reason + preferred) as the R7 mechanism; candidates()/choose() unchanged in contract — avoids double random draws in half-open — cost if wrong: one extra public-ish method on Router.
- Ruling: R18 — accept AttemptRegistry.supersedeWithPaid (failed-then-paid within one gateway order resolves to paid; the earlier failed outcome stays counted for health) — Razorpay allows in-order retries, dropping the later success would hide a real payment — cost if wrong: one gateway order can contribute two health outcomes.
- Ruling: R19 — accept "retryOf must share orderId" → ValidationError — prevents routing a retry from an unrelated order — cost if wrong: none.
- Ruling: R20 — Razorpay late-payment double charge after a retry is a documented v1 limitation (README "Not in v1"/safety section, Task 9): detection via order.multiple-payments within the 24h in-memory TTL, not prevention — Razorpay orders can't be cancelled — cost if wrong: consumers who ignore the event may need manual refunds.
- Ruling: R21 — accept process.emitWarning as the default reporter for throwing listeners, overridable via onListenerError — standard Node mechanism, never silent — cost if wrong: stderr line in apps with buggy listeners.
- Ruling: R22 — retries are allowed only for the LATEST attempt of an orderId; add RetryNotAllowedReason values "superseded" (retryOf is not the latest attempt) and "in-progress" (another createPayment for the same orderId is in flight); take a per-orderId in-flight lock synchronously before the first await and release it in finally; re-check paid-per-order after the awaits — closes the sequential and concurrent double-charge paths the reviewer found — cost if wrong: a legitimate parallel retry is refused and must be retried by the caller.
- Ruling: R23 — emit a dedicated `{ type: "route.all-down"; method; chosen: GatewayName }` event whenever routing picks the least-bad gateway because nothing is usable (spec §6.3 says "emit an event"), in addition to attempt.created.reason — cost if wrong: one extra event type.
- Ruling: R24 — accept: a createPayment without retryOf for an orderId that still has an unexpired attempt is refused ("superseded"); further payments on that order must use retryOf = latest attempt — enforces "never two payable orders" — cost if wrong: callers must pass retryOf; documented in README (Task 9).
- Ruling: R25 — Task 8 Step 4 (running sandbox smoke tests with real keys) needs accounts only Nihar can create; the implementer writes the env-gated smoke tests and verifies they skip cleanly without keys; Step 4 is deferred to Nihar and the README's "Tested against" lists only what has actually run — cost if wrong: v1.0.0 can't be published until Nihar runs them.
- Ruling: R26 — Task 9 Steps 4–5 (create the public GitHub repo, push, npm publish, pin, edit profile README) are outward-facing publishes that need Nihar (accounts + approval); the Task 9 implementer does Steps 1–3 and 6 only. package.json gets version 1.0.0 but nothing is published until Nihar runs the sandbox tests and approves — cost if wrong: release waits on the owner.
- Ruling: R27 — a previous attempt with status "created" (checkout dismissed, no payment) is retryable: if the adapter has cancelOrder (Cashfree) the order is terminated first (same as failed); for Razorpay it's allowed under R20 (detect via order.multiple-payments, not prevent). "pending" stays refused. Add `guard.resume(attemptId)` returning the stored checkout for an unexpired, non-final latest attempt so a dismissed checkout can be reopened; fix the browser example's ondismiss to resume instead of retry. Challenges the plan's "pending or created → refuse" — refusing created added no safety (Cashfree is terminated anyway; Razorpay failed orders are equally payable) and made a common path a lost sale — cost if wrong: Razorpay created→retry widens the R20 detect-only window slightly.
- Ruling: R28 — checkRetry settles the previous attempt from its fetched StatusResult (failed → settle with classification/reason; paid → settle paid) before refusing/proceeding, once-only via markFinal; README gains a "Webhooks to enable" list (Razorpay payment.captured + payment.failed; Cashfree PAYMENT_SUCCESS_WEBHOOK, PAYMENT_FAILED_WEBHOOK, PAYMENT_USER_DROPPED_WEBHOOK) and notes order.paid yields "other" — cost if wrong: none.
- Ruling: R29 — fold these final-review minors into the single fix wave: constructor validation of gateways/priority (ValidationError); Razorpay createOrder pre-checks amount ≥ 100 paise (mirror R12) so customer input can't push health; verifyWebhook rejects non-string/non-Uint8Array bodies with ValidationError("pass the raw body"); remember a cancelled attempt so a second retry doesn't re-cancel; README: auto-capture assumed for Razorpay, phone required for all gateways, NoGatewayAvailableError, CI/lint claims worded truthfully (not yet run; prettier+tsc, no ESLint), public exports (fetchJson/Router/AttemptRegistry) documented as for custom adapters; fix gen-readme-tables pipe escape ("\|"). Deferred: retry-fallback signal (Minor 7) — cost if wrong: small scope growth in the fix wave.
- Ruling: R30 — accept resume() refusals: unknown/expired id → RetryNotAllowedError("unknown-attempt"); final-failed attempt → "superseded"; `gateways: {}` with injected adapters stays valid — consistent with existing reasons, documented — cost if wrong: callers see "superseded" where a dedicated reason would be clearer.
- Ruling: keeps the strictness (silent never-used gateway was the original bug); documented — cost if wrong: users must list every configured gateway.
- Ruling: acceptable for an example; gateway retries surface the misconfiguration — cost if wrong: copy-paste users see 500s until they fix body parsing.
- Ruling: UX only, never a double charge — cost if wrong: customer sees an expired checkout and retries.
